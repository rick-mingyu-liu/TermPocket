# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

TermPocket (the repo and its infrastructure — Render, Neon, the `mindgo` database names — are still named MindGo; the Vercel project was renamed to `termpocket`, so its preview URLs start `termpocket-git-`) is a personal finance app: an Express/PostgreSQL REST API (`backend/`), and a Next.js/TypeScript frontend (`frontend/`). The two are separate npm projects with independent `package.json` files — run commands from within the relevant subdirectory. They are deliberately *not* npm workspaces: workspaces consolidate every lockfile at the repo root, which breaks `npm ci` for both deploys, since Render builds with root directory `backend` and Vercel with `frontend`.

## Commands

### Backend (`cd backend`)
```bash
npm install            # also builds: `prepare` runs tsc into dist/
npm run build          # clears dist/, then tsc → dist/ (CommonJS). Source is TypeScript: docs/superpowers/specs/2026-09-17-backend-typescript-design.md
npm run dev            # tsx watch app.ts (plain node cannot require the .ts modules)
npm start              # node dist/app.js (production — the compiled output, which is .js)
npm run db:setup       # create schema from db/schema.sql (idempotent, CREATE IF NOT EXISTS)
npm run db:seed        # (re)seed the demo account (john.doe@example.com / password123)
npm run db:migrate     # apply pending db/migrations/ and record them (--status, --baseline NNN); direct endpoint only, never -pooler
backend/scripts/rehearse-linux.sh [--live]  # from the repo root, with docker-compose.test.yml up: Render's npm ci + build + preflight in a fresh node:<.node-version> Linux container
npm run agent:eval     # opt-in paid Pocky evaluation: 70 fictional cases, real runtime/DeepSeek, in-memory records (no DB); README "Evaluating Pocky"
npm run agent:preflight  # read-only Pocky deploy check (config incl. which `AGENT_RUNTIME`, DB/migrations 013-015, SDK binary or the direct client, DeepSeek reachability); `-- --live` adds one fictional model turn through the active runtime. Runbook: README "Deploying Pocky to production"
npm run lint           # eslint . (eslint 9, flat config in eslint.config.mjs; TypeScript only, via typescript-eslint)
npm test               # builds, then node --test 'dist/test/**/*.test.js' — unit tests always run; see below for the integration suite
```

### Frontend (`cd frontend`)

```bash
# There is still no `npm test` in the frontend, despite README claims.
```

## Backend architecture

Request flow: **route → (auth middleware) → validation → controller → service/db**. [backend/ARCHITECTURE.md](backend/ARCHITECTURE.md) has the diagram, the patterns in use, and where the layering still leaks.

- **TypeScript**, compiled to **CommonJS in `dist/`** by `tsc` (`module: nodenext`, no `"type": "module"` in `package.json`). `dist/` is gitignored and is what `npm start`, `npm test` and `db:setup` run; `npm run dev` runs the source through `tsx`. Conventions, all of which the conversion preserved deliberately (spec §4.1):
  - **Export shape is the CommonJS one.** A module that was `module.exports = <single value>` is `export = value` — every router and controller, `config`, `logger`, `errorHandler`, `auth`, and the service singletons — and is imported with `import x = require('./x')`, not `import x from`. A module that was `module.exports = { a, b }` uses named exports and an ordinary `import { a } from './x'`. **`export default` is used nowhere**, and changing an export shape is out of scope.
  - **[backend/types/](backend/types/) holds the shared types**: [types/db.ts](backend/types/db.ts) (one interface per table — see the Database section; it is edited with `schema.sql` and every migration), [types/express.d.ts](backend/types/express.d.ts) (merges `AuthUser` into Express's own `Request`, which is why a controller reads `req.user.userId` with no cast), and [types/import.ts](backend/types/import.ts) (the screenshot parser's vocabulary).
  - **Row types are named at the call site**: `query<TransactionRow>(sql, params)`. `query()` is generic but cannot infer a shape from a SQL string, so an unparameterised call gives you `QueryResultRow` and nothing useful.
  - **On the import, MCP, access-token and agent paths, a caught error reaches a log only through `errorSummary(e)`** ([backend/utils/errorSummary.ts](backend/utils/errorSummary.ts)), which yields `{ error, code }` and never the message — a pg error's message can quote the row that failed. It is the shared form of the `{ userId, error, code }` objects these endpoints log (MCP tool errors also include the tool name). **Everywhere else a caught error is still passed whole** to `console.error`/`logger.error` — about 57 sites — and `logger.error` prints its stack, message included. So this is a rule those paths keep, not an invariant the backend has: elsewhere, error messages still reach logs.
  - **Anything reading a file that is not code** — `schema.sql`, test fixtures, `eval/` — resolves from `packageRoot(__dirname)` ([backend/utils/packageRoot.ts](backend/utils/packageRoot.ts)). A path built from `__dirname` alone points into `dist/` once compiled, where those files were never copied.
  - **No `any`.** `@typescript-eslint/no-explicit-any` is an error and there are no `eslint-disable`s for it. `strict`, `noUncheckedIndexedAccess`, `noUnusedLocals` and `noUnusedParameters` are all on.
- [backend/app.ts](backend/app.ts) wires helmet, morgan, cors, JSON parsing, mounts routers under `/auth`, `/transactions`, `/summary`, `/goals`, `/import`, `/access-tokens`, `/mcp`, `/agent`, then global error + 404 handlers. On startup it also calls `schedulerService.init()`.
- **All config is centralized** in [backend/config/index.ts](backend/config/index.ts) — ports, JWT settings, cron schedules, data-retention windows, validation limits, and API keys. Read env vars from here, not `process.env` directly, when adding features.
- **Auth**: [backend/middleware/auth.ts](backend/middleware/auth.ts) verifies the `Authorization: Bearer <token>` JWT and sets `req.user`. Protected routers apply it globally with `router.use(auth)` at the top of the route file (see [backend/routes/transactions.ts](backend/routes/transactions.ts)). Controllers read the user id as **`req.user.userId`**.
- **Account deletion** (`DELETE /auth/account`, Settings → Danger zone → Delete account): [backend/services/accountService.ts](backend/services/accountService.ts) re-checks the password with bcrypt under a `FOR UPDATE` lock on the user row, then deletes, on one dedicated client in one transaction, the user's rows in every table of `OWNED_TABLES` (children first; tables missing before 013/015 are skipped via `to_regclass`), then the user row (preferences and `transaction_retention_terms` with it). Everything also cascades from `users`, but the explicit deletes make the result independent of the deployed FK actions and give the audit line its per-table counts; **a new table with a `user_id` must be added to `OWNED_TABLES`** — `accountDeletionDb.test.ts` fails otherwise. Wrong password is **403** `account_password_incorrect` (not 401, which the client turns into a logout), the demo account 403 `account_demo`, a vanished user 404. It logs the user id only on refusal and `logger.audit('Account deleted', { userId, deleted })` (counts) on success; the 400 for a bad body omits the submitted value. Per-user limiter `RATE_LIMIT_ACCOUNT_DELETE_MAX` (5 per 15 minutes), not `authLimiter`. After COMMIT the controller calls `accountDeleted(userId)`; routes/agent.ts registers `abortOwned` there, so that user's turns in this process stop at once — elsewhere a turn fails at its next `assertActive` or at `finishTurn`, because its run row is gone.
- **Terms acceptance** ([backend/services/termsService.ts](backend/services/termsService.ts), migration `017`): `users.terms_version`/`terms_accepted_at` record which Terms of Service + Privacy Policy version a user accepted; `config.legal.termsVersion` (a date, by convention the `updated` date in `legal.json`) is the current one. Sign-up has a required, unticked box and sends `accept_terms: true`, which stores the version in the INSERT (anything but boolean `true` stores nothing, and the user is asked later instead). `GET /auth/terms` answers `required` when the stored version differs — once per version, never at every login — and never for the demo account (shared) or before 017 (probed like 016, positive answer cached). `POST /auth/terms {version}` stores only the current version (409 `terms_version_mismatch` otherwise, so a card left open across a terms change cannot record text the user never saw). [frontend/components/TermsGate.tsx](frontend/components/TermsGate.tsx), mounted in `_app.tsx`, shows the undismissable accept card (I agree / Log out) on every signed-in page except the public ones, and lets the app go on if the status cannot be read. **Changing `termsVersion` asks every account again**, so change it only for edits users should re-accept. Acceptance is **recorded, not enforced**: the API serves a user who has not accepted, and only the frontend card asks. `test/termsAcceptance.test.ts` covers both routes and the register INSERT, and `termsMigration.test.ts` applies 017 twice to a pre-017 schema with rows and twice to a fresh one.
- **Email addresses are normalized on every lookup**: registration stores `normalizeEmail()`'s form (lowercase; Gmail without dots or `+tag`), so `/login` and `/resend-verification` normalize the same way, and also try the address as typed (`res.locals.typedEmail`, for accounts created before normalization existed, 2025-06-28 to 07-04), preferring the normalized match. A JWT's `email` claim and any mail use the stored address. `test/emailNormalization.test.ts`. A new route that looks a user up by address must do the same.
- **Validation**: use `express-validator` `body([...])` arrays in the route file, then check `validationResult(req)` at the top of the controller method. Query parameters take `query([...])` the same way — `GET /transactions/retention-preview` and `GET /transactions` do so far. The latter takes `page` (1–1,000,000), `limit` (1–200, default 50) and an optional `before` cursor, each given at most once; it orders by `date DESC, id DESC` (stable on ties) and the transactions list page pages with `before` (the opaque `nextCursor` of the previous response, base64url of `YYYY-MM-DD|id` from `utils/transactionCursor.ts`, null when no more) because OFFSET skips or repeats rows when data changes between pages. `GET /transactions/:id` returns one owned row or 404 (registered after the literal routes).
- **Terms**: [backend/utils/terms.ts](backend/utils/terms.ts) is the single definition of the Waterloo term calendar (Winter Jan–Apr, Spring May–Aug, Fall Sep–Dec). `GET /summary/rolling` takes **exactly one** of `?term=2026-spring|current|previous`, `?year=2026|current|previous`, or `?months=N` — passing more than one is a 400 — and echoes `term`, `year`, `periodLabel`, `termLabel`, `startDate`, `endDate` so a client never computes a date or a name. **A year is three terms**, not twelve rolling months: the terms tile Jan–Dec exactly, so `?year=2026` shares its boundaries with Winter/Spring/Fall 2026 and its totals are always their sum. The dashboard's period selector (This term / Last term / This year / Last year) defaults to `term=current`. Anything needing term boundaries — the summary views, and the automatic-deletion sweep (`services/retentionService.ts`) — must go through it rather than computing its own, because a view and a deletion that disagree about where a term starts would fail silently. Bounds are half-open `[start, end)`, matching the `date >= $1 AND date < $2` queries. **Do not build dates with `new Date(y, m, d).toISOString()`** anywhere: it is off by a day east of UTC. All known instances are gone (items 21 and 23); use integer arithmetic, or `toDay()` from `utils/dates.ts` when starting from a `Date`.
- **Address validation at registration**: [backend/services/emailValidationService.ts](backend/services/emailValidationService.ts) exports one function, `validateEmail(email)` → `{ valid, reason?, source }`. MailboxLayer where `MAILBOXLAYER_API_KEY` is set, its own 30-domain disposable list otherwise. **It never throws and never blocks on its own failure** — no key, a network error, an HTTP error, an apilayer error payload (HTTP 200 with `success: false`) or an unrecognised response shape all fall back to the domain list, loudly via `console.error`. The previous version turned each of those into a rejected or 500ing registration. Keep that property if you touch it: `test/emailValidation.test.ts` has a case per failure mode. A failed SMTP probe (`smtp_check: false`) is **not** a rejection — university and company mail refuses probes, and the verification email proves deliverability; only bad format, disposable, or no MX (bar major providers) is refused.
- **Log levels**: [backend/utils/logger.ts](backend/utils/logger.ts). `info`, `warn` and `debug` are gated on `config.logging.enableConsoleLogs` = `NODE_ENV === 'development'`, so **they print nothing in production**. `error` and `audit` always print. Use `logger.audit` only for events that destroy or irreversibly change user data — the retention deletions do, which is why they moved off `info`. `LOG_LEVEL` is close to inert: it gates `debug()` and nothing else.
- **Logging user data**: **never log a credential** — verification tokens, JWTs, password hashes. For addresses, the rule is *log a user id where one exists, and a masked address only where one does not* (before the INSERT, or when a lookup found nothing). `maskEmail()` in [backend/utils/privacy.ts](backend/utils/privacy.ts) produces `j***@example.com`. Registration leaked verification tokens this way once; `test/registerLogging.test.ts` guards it by running the real handler and inspecting everything it printed. The access log is a log too: `app.ts` uses `combined`'s fields but prints `:url` and `:referrer` through `redactUrl()` ([backend/utils/redactUrl.ts](backend/utils/redactUrl.ts)), because the stock format wrote every `GET /auth/verify-email/<token>` and its `/verify-email?token=` Referer to Render's logs. A new route that takes a credential in its path needs a rule there; secret query parameters (`token`, `key`, `password`, ...) are already covered.
- **Zone-less timestamps are UTC**: `users`, `transactions`, `savings_goals`, `import_batches` and `access_tokens` use `TIMESTAMP` without a zone. `db/connection.ts` runs every session in UTC (`SET TIME ZONE 'UTC'` next to `search_path`), parses `TIMESTAMP` as UTC and writes `Date` parameters as UTC (`parseInputDatesAsUTC`). Before that, both directions were right only when the Node process also ran in UTC: on a Toronto-time machine an email verification link expired four hours late. `test/dates.test.ts` pins the parser across four timezones.
- **Dates are days, not instants**: `db/connection.ts` registers a `pg` type parser so a `DATE` column arrives as the plain string `'2026-08-28'`. Without it node-pg builds a `Date` at the *server's* local midnight and `res.json()` re-serialises that in UTC, so one stored day left the server as a different string per host and every viewer west of it read the day before. Consequences worth keeping in mind: **never `new Date(day).getMonth()`** — a plain `'2026-08-01'` parses as UTC midnight and answers July west of UTC, which silently files a month of transactions under the month before. Use [backend/utils/dates.ts](backend/utils/dates.ts) (`toDay`, `monthOf`, `formatDay`, `monthSpan`) on the backend and [frontend/lib/date.ts](frontend/lib/date.ts) (`toDay`, `formatDay`, `formatDayRange`, `todayDay`, `daysUntil`) on the frontend. Both accept `'2026-08-28'` and `'2026-08-28T00:00:00.000Z'`, so a stale deploy of either side still renders the right day. The frontend copy has no test — the frontend has no runner — but the backend twin is covered by `test/dates.test.ts`.
- **DB access**: [backend/db/connection.ts](backend/db/connection.ts) exports `query(text, params)`. Notable pattern: the `pg` Pool is **lazily created and auto-closed after 5 minutes of inactivity** to save connections. Always use parameterized queries (`$1, $2, ...`); controllers build filtered queries by incrementing a `paramCount` (see `getTransactions`).
- **Multi-currency**: monetary rows store a `currency` column; conversion happens at read time via `services/exchangeRateService.ts`. Allowed currencies: `CAD, USD, EUR, GBP, AUD, CNY`.
- **Removed features**: the stock watchlist and one-shot AI Planning are gone, code and storage. The `/investments` and `/ai` routers and `POST /goals/from-ai-plan` are no longer mounted, so those paths get the global 404 (`removedFeatures.test.ts`). ### Conversation recording

The implemented `/agent` slice records actual income/spending in English, Chinese or mixed text, supports corrections to one editable pending batch, persists conversations across visits, answers plain-text questions about the user's own recorded income and spending through three read-only tools, and helps plan through deterministic projections and button-confirmed savings-goal proposals (Planning, below). The composer also takes English voice dictation, transcribed on the device (below). There are no durable facts, conversation summaries or stored financial plans. Do not advertise those deferred features or restore retired stock/one-shot planning.

- [routes/agent.ts](backend/routes/agent.ts) owns orchestration and strict application JSON validation; every endpoint, including status, requires the login JWT. IDs from requests are always bound to `req.user.userId`. All responses are `no-store`; errors expose stable `agent_*` codes, never SDK/provider payloads.
- [services/agent/store.ts](backend/services/agent/store.ts) owns short database transactions, ownership locks, run admission, immutable draft revisions, confirmation and undo. Never keep a DB transaction open during model execution. Compound owner/conversation foreign keys defend associations too. [types.ts](backend/services/agent/types.ts) defines the application contract; [validation.ts](backend/services/agent/validation.ts) checks positive decimal strings, real calendar dates, the six currencies, and categories matching income/expense.
- [services/agent/runtime.ts](backend/services/agent/runtime.ts) lazily loads pinned Claude Agent SDK `0.3.300` with Zod `4.6.7` and DeepSeek `deepseek-flash`. It exposes `propose_transactions`, replacing the whole pending batch, three read tools (below) and four planning tools (Planning, below). It has no financial-write tool or DB access; the server-owned `assertActive` callback checks revocation before each invocation. Built-in tools/settings are disabled, unknown tools denied, and a hook counts attempts even when schema validation rejects them. **Thinking is disabled in the request body itself** (`CLAUDE_CODE_EXTRA_BODY={"thinking":{"type":"disabled"}}`): the SDK's `thinking:{type:'disabled'}` makes the CLI *omit* the field, and `deepseek-flash` reasons by default when it is absent — 4–9k hidden characters per round trip that count against the output-token and assistant-character budgets. That is what failed a production planning turn with `agent_limit_exceeded` after 31 s; do not drop the env var. When a limit trips, the runtime logs `Agent run hit a limit` with a `reason` (`tool_calls`, `tool_attempts`, `tool_output_chars`, `total_tokens`, `output_tokens`, `assistant_chars`, `final_chars`) and counts only, and the `AgentError` carries `usage` so `failTurn` records the failed run's tokens and executed tool calls (capped at 8, the column's check); the client still sees only the code. Spawn receives a closed environment allowlist and isolated temporary config/cwd; `persistSession:false` and cleanup prevent hidden SDK transcript storage. Never pass inherited credentials/configuration or log raw events. Only actual token counts are recorded; SDK dollar estimates are not authoritative DeepSeek billing. The reply language is decided server-side (`replyLanguage()`): an explicit `en`/`zh` setting wins; `auto` follows the current message's own words (each Han character and each Latin word count one, ties go to Chinese, so code-switched Chinese such as “在Costco买了groceries” stays Chinese), falling back to the latest user message with words only when the current one has none, then English. The envelope carries the result as `context.reply_language`, never the raw setting, because the model once answered an English message in Chinese under `auto`.
- **Two runtimes, one turn** (`AGENT_RUNTIME=sdk|direct`, `config.agent.runtime`, read per turn by `runAgent`; default `sdk`, and anything but `direct` means `sdk`). `createAgentRuntime` is the SDK path above. `createDirectRuntime` runs the same loop in-process with the plain `@anthropic-ai/sdk` client (pinned `0.131.0`, created once, every option explicit: DeepSeek key, `authToken:null`, `logLevel:'off'`, two retries): `messages.create` with the same `systemPrompt`, the same envelope from `prompt()`, the eight tools' input schemas from `z.toJSONSchema` of the same zod shapes, `max_tokens` = `maxOutputTokens`, `thinking:{type:'disabled'}` and the turn's AbortSignal (deadline + cancellation). Each tool handler, and `assertActive` in `admit()`, is raced against the turn's abort too, so a hung query or rate lookup cannot hold the turn or its process slot past the deadline; its late result is discarded. No child process, temp directory or env allowlist, and no host date in the request — the SDK's CLI injects the host's date, which the direct path cannot. **Everything else is shared, in `openTurn()`**: the tools and handlers (`admit()` = `assertActive` then the call budget), `attempt()` (the PreToolUse hook's attempt gate, which the direct loop applies to every `tool_use` block in order, unknown names and schema failures included), `observe()` (real usage per response, `total_tokens`/`output_tokens`/`assistant_chars`), `finish()` (`invalidProposal`, `final_chars`, empty reply) and `failure()` (`errorSummary`, then `agent_provider_error`). Change a guard there and both runtimes get it. Direct-only rules: unknown tools answer `agent_unknown_tool`, schema failures answer `agent_invalid_input` naming field paths and zod codes (never values) and the turn goes on; `stop_reason` `max_tokens` ends the turn as `agent_limit_exceeded` (reason `max_tokens`; the SDK's CLI would continue and overrun `maxOutputTokens`), more than `maxTurns` model turns as reason `max_turns`, any other non-`end_turn` stop as `agent_provider_error`. Delete the SDK path, not `openTurn`, when `sdk` is retired.
- **Investigation** ([services/agent/investigation.ts](backend/services/agent/investigation.ts)): `spending_summary` (one window's income, spending, net and every category), `compare_spending` (two windows; differences are b − a, ratios b / a and null with a note when a is zero) and `transaction_details` (a page of rows, newest first, keyset-paginated on `(date, id)` with an opaque cursor bound to the window and filters). The route binds them to `req.user.userId` (`recordsFor`) and passes them in as `AgentInput.records`; the runtime never imports `db` and no tool argument names a user. Windows are half-open real calendar days, at most 1827 days; currency, category and type are validated against the agent's canonical lists; `limit` is 1–25 (default 15). Each row's description reaches the model only as `description_untrusted`: control characters and bidi overrides become spaces and it is clipped to 80 characters. Totals aggregate in SQL through `moneyFacts.groupedBetween` (shared with MCP, whose output is unchanged) and are summed in integer cents. Conversion uses current rates and says so in `conversion_note`; a missing, zero, negative or non-finite rate, or a provider that does not answer within 5 s, makes the tool answer `agent_rate_unavailable`, never a silent wrong number; `RateUnavailableError` keeps the cause's `code` (not its message) for `errorSummary`. Read calls share the eight-call and 16,000-character tool-output budgets with proposals, never touch the pending draft, and answer errors with a code only (`agent_invalid_input`, `agent_rate_unavailable`, `agent_records_unavailable`). A read result larger than the remaining budget is refused as `agent_output_budget` (narrow the window, filter, or summarise) without ending the turn; cumulative overflow still stops it with `agent_limit_exceeded`. The prompt envelope carries `context.calendar` — today, current and previous term, current-term-so-far and the previous term's same-elapsed window (`terms.sameElapsedWindows`, shared with MCP's pace) and the year — so the model never computes dates. **Descriptions, amounts, dates and categories of matching records go to DeepSeek**; the system prompt treats descriptions as third-party text never to be followed, forbids reading records from changing `pendingRows` unless the user's own current message describes a new transaction, requires every number to be quoted from a tool result with its window and currency, and requires plain text with no Markdown because the UI renders raw text.
- Only `POST /agent/conversations/:id/confirm` inserts transactions with `source='agent'`. It binds version, selected row IDs and request UUID; repeated matching requests return existing state. Chat text such as “yes” has no confirmation authority. Partial confirmation creates a new revision for remaining rows. Undo within ten minutes requires every saved transaction's exact PostgreSQL timestamp and tuple version to match; do not round timestamps through JavaScript `Date`.
- **Planning** ([scenario.ts](backend/services/agent/scenario.ts), [planning.ts](backend/services/agent/planning.ts), `spendingBaseline`/`listGoals` in investigation.ts): four more tools in the same `draft` server, under the same eight-call and 16,000-character budgets and the same `assertActive` check. `spending_baseline` averages income, expenses, net and each category over the last 1–12 (default 3) whole calendar months before the conversation's today, divided by the months with any record (like `moneyFacts.monthlyBaseline`), in cents through `groupedBetween`. `list_goals` returns at most 20 goals (target date nulls last, id) with named columns, `description_untrusted` cleaned and clipped like transaction descriptions, and `updated_at` as fixed-width microsecond text (`to_char(updated_at,'YYYY-MM-DD HH24:MI:SS.US')`, `GOAL_VERSION_SQL` in planning.ts, used by listing, proposing and confirming alike) — the version a proposal must quote. An amount that does not parse is an error (`agent_records_unavailable`), never a zero. `calculate_scenario` is a pure projection in integer cents over day strings (no `Date`): window `[start, end_exclusive)` ≤ 731 days, 1–40 events with weekly, `two_weeks` (biweekly pay: every 14 days, not twice a month) or month-end-clamped monthly repeats, ≤ 600 occurrences in the window, events in other currencies converted once per event at a listed current rate (`agent_rate_unavailable`, never a silent 1), end-of-day balances (the start day included, after its own events), lowest point, reserve shortfall and first breach, per-event `event_counts` (each input event's `index`, `label`, `kind`, `occurrences` inside the window and `first_date`/`last_date`, so the prompt can require any count of paydays or payments to be quoted rather than counted by the model), and goal math (`months_left` in whole calendar months, so `monthly_needed` is conservative and rounded up to the cent; a past deadline needs everything now). Without `starting_cash` it returns `status:'incomplete'`, `missing:['starting_cash']` and no balances; the prompt forbids affordability claims then. `propose_goal` validates one create or update, matching the goal form (create: no id, a target date that is required and not in the past; update: `goal_id` and `expected_updated_at` from `list_goals`, omitted optional fields keep their values, the target date cannot be cleared and a changed one may not be past, `current_amount` may exceed the target only if unchanged, a no-op is refused) and, for an update, reads the owned goal for a `before` snapshot; another user's goal is `agent_goal_not_found`, a stale version `agent_goal_conflict`. Its failures are repairable tool errors with fixed hints, not turn failures. A successful proposal travels in `AgentResult.goalProposal` and is stored only by `finishTurn`, after `active()`, so a cancelled or expired run cannot publish it; it supersedes the conversation's pending proposal. `ConversationState.goalProposal` is the conversation's most recent proposal (null if that one is superseded), with a pending one past `expires_at` reported as `expired` by the DB clock. Only `POST /agent/conversations/:id/goal-proposal/confirm` (`{proposalId, requestId}`) writes `savings_goals`: under `owned()`, exact replay returns state, a reused request ID for another proposal is `agent_request_conflict`, an active run `agent_busy`, a non-latest or decided proposal `agent_version_conflict`, an expired one `agent_expired`; a create whose target date is before today in the conversation's timezone (`(now() AT TIME ZONE timezone)::date`) commits `status='conflict'` and answers 409 `agent_goal_invalid`; an update locks the goal `WHERE id AND user_id` and compares `updated_at::text` exactly, otherwise it commits `status='conflict'` and answers `agent_goal_conflict` (a deleted goal too). `DELETE …/goal-proposal` (`{proposalId}`) cancels the pending one. Both need storage, not the provider key. Proposals expire after 24 hours; the hourly sweep stores that as `status='expired'` and deletes decided, expired and superseded proposals 30 days after `decided_at`, inside a savepoint so its failure cannot roll back the other cleanups. The scenario and goal values the model states go to DeepSeek like any other message content.
- Admission is one live run per user, 20 new turns per rolling hour and 60 per rolling 24 hours per user (`AGENT_MAX_TURNS_PER_DAY`, `agent_daily_limit`), and 600 per rolling 24 hours across all users (`AGENT_MAX_TURNS_PER_DAY_ALL_USERS`, `agent_daily_capacity`), all counted in PostgreSQL from `agent_admissions`. The all-users count runs under a transaction-level advisory lock (`ADMISSION_LOCK` in store.ts) taken after the owner lock, so concurrent users cannot overshoot it; the 24-hour count scans the table (its index leads with `user_id`), which the 30-day sweep keeps small. Receipts retain IDs, request hashes and exact row versions, not amounts/descriptions. ### Database

**Demo data is generated, not hardcoded.** [backend/db/demoData.ts](backend/db/demoData.ts) builds the demo account relative to `new Date()` — five terms of a Waterloo co-op student, alternating study and work terms, with the current term truncated at today. It exists because the old `seed.sql` hardcoded dates in 2025, so by August 2026 the demo's default window (`?term=current`) was empty and all three savings goals showed as overdue. Amounts are jittered by a seeded generator keyed on term and category, so the same day always produces identical data. `db:seed` **replaces** the demo user's rows inside one transaction using a dedicated client (`db.getPool().connect()` — `db.query` would put `BEGIN` and `COMMIT` on different pooled connections); the old seeder relied on `ON CONFLICT DO NOTHING`, which caught nothing because those tables have no unique constraint, so a second run duplicated every row. `db:seed` is the only entry point permitted to create the account; the scheduled refresh passes `create: false` and will not conjure its own target.

**The scheduled refresh is opt-in** (`DEMO_REFRESH_ENABLED=true`) and **staleness-driven**: each hourly maintenance run issues one aggregate `SELECT` (`DEMO_FRESHNESS_SQL`) and refreshes (`refreshDemoAccountIfStale()`) when the `is_demo` user has no transactions, or when the earliest `created_at` among them is more than `config.demo.staleDays` days before the database's `now()` in UTC (`DEMO_REFRESH_STALE_DAYS`, default 14, never below 7). It measures the last refresh, not the newest row: the demo login is public, the refresh inserts every row in one statement, rows a visitor adds are created later and edits leave `created_at` alone, so adding or editing rows cannot postpone a refresh that is due. A visitor can only move it by deleting every refreshed row, and then only to the creation time of their own oldest row. `test/demoFreshnessDb.test.ts` runs the statement against PostgreSQL inside rolled-back transactions. It used to be its own 30-day `scheduleInterval`, whose clock restarted with every deploy, so on Render it never ran. With no `is_demo` user it writes nothing and logs one error per process. The write itself lives in [backend/services/demoAccountService.ts](backend/services/demoAccountService.ts), shared by both callers so they cannot drift. It resolves the demo account by the **`is_demo`** column (migration `007`, unique partial index — at most one), never by email: `john.doe@example.com` is an ordinary address nothing reserves, and a timer pointed at a guessable string would wipe a real account's data monthly with nobody watching. Run by hand that exposure is bounded because a human is present; on a schedule it is not. The first `db:seed` after migration 007 adopts the existing demo row by setting the flag on it. The refresh throws rather than logging and returning, like `cleanupService`, and returns its **deleted** row count so the maintenance run's `attempt()` audits the destructive half per decision D; a failed refresh is logged as `demoRefresh failed` without stopping the other cleanups.

Schema lives in [backend/db/schema.sql](backend/db/schema.sql) and is applied wholesale by `db:setup`, which is idempotent and safe to re-run. Migration `017_terms_acceptance.sql` adds `users.terms_version` and `users.terms_accepted_at` (NULL = never accepted); additive and idempotent, deploy the code first (it tolerates their absence). Tables: `users`, `transactions`, `savings_goals`, `import_batches`, `access_tokens`, `agent_conversations`, `agent_messages`, `agent_runs`, `agent_drafts`, `agent_receipts`, `agent_admissions`, `agent_goal_proposals` (`watchlist` and `ai_plans` were dropped by migration `014`; deploy code before applying it). Migration `016_transaction_retention.sql` adds `users.transaction_retention_terms` (SMALLINT, NULL = off, CHECK 3–12): additive and idempotent; deploy the code first (it tolerates the column's absence, see Scheduler), then apply it through the direct endpoint. Migration `015_agent_goal_proposals.sql` is recommended before deploying the planning backend, but not required: the store probes `to_regclass('agent_goal_proposals')` (caching only a positive answer, so applying 015 later needs no restart) and, while it is absent, conversations read with `goalProposal: null`, `propose_goal` answers `agent_unavailable`, the confirm/cancel routes answer 503 `agent_unavailable`, and the sweep skips the table. 015 is additive, idempotent, guarded for PostgreSQL 15 and refuses to run before `013`. `updated_at` is auto-maintained by triggers. `transactions.source` (migrations `011` and `013`) is `manual`, `ocr`, `ocr_llm`, or `agent`; `POST /transactions` and `PUT /transactions/:id` do not accept it. Import and agent confirmation set their own source. PostgreSQL 15+ is required for migration `013`'s column-specific `ON DELETE SET NULL`. Verify the migration on local/staging first; production application remains a separate operator action. `schema.sql` is the desired end state; incremental changes against an existing database go in [backend/db/migrations/](backend/db/migrations/) as numbered files (`NNN_name.sql`), applied by `npm run db:migrate` ([backend/db/migrate.ts](backend/db/migrate.ts)), which records each file and its SHA-256 in `schema_migrations`, runs on one connection under an advisory lock, stops at the first failure with that file unrecorded, and refuses an empty database (`db:setup`'s job; on a fresh database it records every migration) or an untracked existing one (`--baseline NNN` records 001..NNN without running them). Never edit an applied migration — `--status` flags a changed checksum; add a new file instead. Each migration still owns its own transaction, so keep new ones idempotent. `test/schemaMigrations.test.ts`. Keep the three in step — the migration, `schema.sql` and [backend/types/db.ts](backend/types/db.ts), which holds one interface per table. A migration without the matching `schema.sql` edit means fresh setups and existing databases diverge; one without the matching `types/db.ts` edit means the row types describe a column that is no longer there, and nothing fails until a controller reads it.

**Connections**: `DATABASE_URL` points at Neon's *pooled* endpoint (`-pooler` in the host); the project lives in AWS `us-east-1`. The Render backend (`termpocket-api`, https://termpocket-api.onrender.com) runs in Render's Virginia region, next to it; until 2026-10-15 it ran in Oregon as `mindgo.onrender.com` (now suspended), so every query crossed the continent. Render cannot move a service between regions: a move means a new service, copied environment variables and a new `NEXT_PUBLIC_API_URL` on Vercel. Every query in this codebase names tables unqualified, so [backend/db/connection.ts](backend/db/connection.ts) issues `SET search_path` on each new pool connection. This is defensive rather than load-bearing today — the AWS pooler hands out a normal `"$user", public` — but Neon's *Azure* pooler handed out an **empty** `search_path`, where every query failed with `relation "transactions" does not exist`. Keep it: it costs one statement per connection and makes the app behave identically on any endpoint. Don't move it into the pool's `options` — Neon's pooler rejects `search_path` as a startup parameter. Use the **direct** endpoint (drop `-pooler` from the host) for `pg_dump`/restore.

## Frontend architecture

- **Vercel builds only when `frontend/` changed**: [frontend/vercel.json](frontend/vercel.json)'s `ignoreCommand` diffs `HEAD^..HEAD` within the root directory. The frontend build reads nothing outside `frontend/` today (the `license` field's `../LICENSE.md` is metadata); if that changes, widen the command or the build will be skipped.
- **Next.js 15 Pages Router** (`pages/`) with React 18. Add screens as files under `pages/`. Dependency security decisions and remaining advisories are recorded in [frontend/DEPENDENCIES.md](frontend/DEPENDENCIES.md).
- **API client**: [frontend/utils/api.ts](frontend/utils/api.ts) is a shared axios instance. A request interceptor attaches the JWT from `localStorage`; a response interceptor handles errors globally — `401` triggers `logout()`, and `403/404/500`/generic errors surface a SweetAlert2 dialog. `/auth/*` endpoints are exempted so components can handle those errors themselves. AI connections handles its own non-401 4xx errors from `/access-tokens`, Settings' Delete account dialog its own non-401 errors from `/auth/account` (wrong password, demo refusal, rate limit, shown inline), and the agent caller handles `/agent` errors; a 401 still logs out. Import this instance rather than calling axios directly.
- **AI connections**: [frontend/components/AiConnections.tsx](frontend/components/AiConnections.tsx) is embedded in Settings. It lists token metadata, and its setup guide dialog shows the deployment's MCP endpoint and header; a newly created secret lives only in component state and is discarded on dismissal or unmount, never put in localStorage.
- **Auth state** is `localStorage` `token` + `user`; there is no server session.
- **UI**: Radix primitives wrapped in [frontend/components/ui/](frontend/components/ui/) (shadcn-style), styled with Tailwind + `class-variance-authority`; use the `cn()` helper in [frontend/lib/utils.ts](frontend/lib/utils.ts) for conditional classes.
- **Transaction categories**: the canonical list is the exported `categories`
  object in [frontend/pages/transactions/new.tsx](frontend/pages/transactions/new.tsx)
  — the edit page and the dashboard both import it, and the dashboard uses it to
  decide whether a category is income or expense (unlisted names default to
  expense). Adding one means four edits, not one: that list, `CATEGORY_COLORS`
  in [frontend/pages/index.tsx](frontend/pages/index.tsx) (or it gets a
  hash-derived colour), and **both** `common.json` files, because the picker
  renders each name through `t(category)`. The manual transaction backend does not validate the
  category against any list; the agent path validates its canonical copy in `services/agent/validation.ts`, pinned by `agentValidation.test.ts`. The seed's copy in
  [backend/db/demoData.ts](backend/db/demoData.ts) is now pinned to this one by
  `test/demoData.test.ts`, which parses this file and compares. The locale
  files are still unguarded.
- **i18n**: `next-i18next` with `en` and `zh` locales in [frontend/public/locales/](frontend/public/locales/). Add user-facing strings to both `common.json` files. **Pages get their translations from `getStaticProps`, never `getServerSideProps`** (`transactions/edit/[id]` adds `getStaticPaths` with `paths: []`, `fallback: 'blocking'`; it reads its id from `router.query` client-side): on Vercel's serverless functions `public/locales` is not in the bundle, so SSR pages shipped an empty `initialI18nStore` (raw keys such as `legalConsent`, `/zh/*` in English). `localePath` in [frontend/next-i18next.config.js](frontend/next-i18next.config.js) is also set to the absolute path on the server, as next-i18next recommends for serverless, but do not rely on it. Check a new page by reading `__NEXT_DATA__` → `pageProps._nextI18Next.initialI18nStore` (about 433 keys).
- **Theme**: light/dark via [frontend/contexts/ThemeContext.tsx](frontend/contexts/ThemeContext.tsx).
- **On-device dictation assets**: `public/voice/worker.js` (committed) imports `/voice/transformers-4.3.1/transformers.min.js` and sets `env.allowRemoteModels=false` and `env.localModelPath='/voice/'`. Transformers.js would fetch ONNX Runtime's `.mjs`/`.wasm` from jsDelivr; the worker keeps its choice of file (asyncify, or plain on Safari before 26 without WebGPU) and rewrites the URL to `/voice/ort-<version>/`, refusing any other version, so nothing is fetched from a CDN or Hugging Face at runtime. Webpack never sees any of it, so OCR's `onnxruntime-web$` alias and `/ort/` (1.30.0) are untouched. The directory names in the worker and in `scripts/voice-assets.js` must change together.
- **On-device OCR**: [frontend/next.config.js](frontend/next.config.js) aliases `onnxruntime-web` to `frontend/lib/ocr/ortRuntime.js`, which loads the runtime with `importScripts` from `/ort/` instead of letting webpack bundle it — Next's minifier cannot parse the library's ESM build. Do not remove the alias. It runs single-threaded on purpose: multi-threaded WASM needs cross-origin isolation, and with isolation headers on, this classic-script runtime hangs starting its thread workers. Chrome throttles OCR to a crawl in a hidden or backgrounded tab; keep the tab visible while it runs.

## Environment

Both projects read `.env` (already present locally, gitignored). Backend needs `DATABASE_URL` (or `DB_*` parts), `JWT_SECRET`, and optionally email credentials (`EMAIL_USER`/`EMAIL_PASS`; `EMAIL_HOST`, `EMAIL_PORT` (default 465) and `EMAIL_FROM` are optional, and unset `EMAIL_HOST` means Gmail), `WEEKLY_REPORT_ENABLED` (unset: production only) and `MAILBOXLAYER_API_KEY`. Conversation recording adds `AGENT_ENABLED` (default false), `DEEPSEEK_API_KEY`, `DEEPSEEK_MODEL` (default `deepseek-flash`), `AGENT_MAX_CONCURRENT_RUNS` (default 1) and `AGENT_RUNTIME` (`sdk` default, or `direct`); only set the flag after agent migration verification. Frontend needs `NEXT_PUBLIC_API_URL`. In production, DB connections use `ssl: { rejectUnauthorized: false }`.

Agent hosting requires (under `AGENT_RUNTIME=sdk` only) a Node process able to spawn the SDK's platform-specific executable, its optional native package installed and writable temporary storage, and (under both) outbound HTTPS to `https://api.deepseek.com/anthropic`, and an HTTP timeout longer than the 90-second model deadline plus cleanup. The pinned adapter has live local acceptance coverage; deployed Linux binaries, resource capacity and provider throttling require host verification. Do not silently enable this feature, migrate production or expose keys in diagnostics.

## Known gaps

Carried over from the improvement backlog, which is now retired — the reasoning
for anything already fixed lives in the comment next to the code, and the rest
is in git history.

- **Nothing guards the locale files against category drift.** Adding a
  transaction category means four edits (see above); `test/demoData.test.ts`
  pins the backend copy to the frontend list, and `check:locales` fails when
  only one `common.json` gains it, but the picker calls `t(category)` with a
  variable its scan cannot see, so a category added to neither file still
  ships untranslated.
- **`LOG_LEVEL` is close to inert** — it gates `logger.debug()` and nothing
  else. Setting it to `error` in production does not silence `info`; the
  `NODE_ENV` check already does that.
- **`/summary/rolling` serialises every transaction in the window twice** and
  aggregates in Node rather than SQL. That cost is per user and per request, so
  it is the gate on offering an *All time* period.
- **The frontend has no test runner**, so `lib/date.ts` is unguarded. Its
  backend twin, `utils/dates.ts`, is covered by `test/dates.test.ts`.
- **Phone OCR speed is unmeasured.** On a laptop (M-series Mac, Chrome,
  visible tab) screenshot import takes about 1–2 s per image; Chrome throttles
  a hidden tab to 8–15 s. A mid-range phone may be several times slower than
  either number — measure on a real device before announcing the feature.
- **The LLM fallback (spec §4.7) was not built.** The private set (seven real
  screenshots, 2026-09-17) is all read by the rule-based parser once each
  layout was added, so nothing yet shows it is needed. `POST /import/parse`
  reports `ai_fallback_unavailable` when the parser is unsure, and the import
  page falls back to showing the recognised text for manual entry. Build it
  only if `npm run benchmark -- --set private` on real screenshots shows a
  gap the parser itself can't close.
- **Uber and Uber Eats imports can double-count** a card charge already
  imported from a bank screenshot; `possible_duplicate` needs the same day,
  amount and currency, so a charge posted a day later is not flagged.
- **Dictation on phones is only partly measured.** On the owner's iPhone (Safari, the round 2 spike page) all 20 test amounts came out right and a few other words did not; latency, load time and the iPhone model were not recorded. First use downloads about 77 MB of model plus a 14–27 MB runtime file (compressed in transit), on top of OCR's 45 MB.
- **First screenshot-import use downloads about 45 MB** (the OCR model plus
  the ONNX runtime). The engine banner shows progress, and HTTP caching keeps
  it to once per browser.
