# Dependency security notes

Audit date: **2026-10-15**. `npm audit` reports **7 high, 2 moderate, 0 critical**
frontend findings; the backend reports zero. Frontend findings propagate from
only two root advisories through their dependent packages. **The zero-high
security gate remains open.** Re-run the audit before treating these counts as
current.

## Framework and PostCSS

Next.js is 16.4.3 (2026-11-04, from Dependabot PR #153), retaining Pages Router
and React 18: Next 16 still accepts `react@^18.2.0` but warns at build time that
React 18 support is deprecated and goes in Next 17, so the React 19 move comes
before that upgrade. It needs Node 20.9+; CI runs 22. Next 14.2.35 still has
critical advisories, including [AVIF image optimization RCE](https://github.com/vercel/next.js/security/advisories/GHSA-2xp9-vwfh-vxw4),
first patched in 15.5.24. `next-env.d.ts` and the `jsx: "react-jsx"` line in
`tsconfig.json` are generated by Next 16.

Next 16 removed `next lint` and builds with Turbopack by default. `lint` now runs
ESLint directly over `pages/`, `components/` and `lib/` (the directories `next lint`
covered), and `dev`/`build` pass `--webpack` so the `onnxruntime-web` alias in
`next.config.js` still applies. eslint-config-next stays at 15.5.28, with ESLint 8
and `.eslintrc.json`: moving to ESLint 9, a flat config and eslint-config-next 16
changes the lockfile and is a separate change.

The override `next → postcss: "$postcss"` replaces Next's exact PostCSS 8.4.31
with the project's direct dependency, currently locked to 8.5.29, to take security
fixes. It deliberately overrides the exact upstream pin within PostCSS major 8,
and is scoped only to Next. Production compilation, server-rendered pages,
locales, assets and redirects passed with this combination on Node 22. Remove
the override when Next's own dependency resolves to a patched version.

## Remaining advisories

**[GHSA-vfj7-8cjw-p6xm](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm), high:**
deeply nested brace patterns can exhaust the stack. Installed paths:

- `tailwindcss@3.4.19 → chokidar@3.6.0 → braces@3.0.3`
- `tailwindcss@3.4.19 → micromatch@4.0.8 → braces@3.0.3`
- `tailwindcss@3.4.19 → fast-glob@3.3.3 → micromatch@4.0.8 → braces@3.0.3`
- `eslint-config-next@15.5.28 → @next/eslint-plugin-next@15.5.28 → fast-glob@3.3.1 → micromatch@4.0.8 → braces@3.0.3`

Braces 3.0.3 is still the latest npm release and no patched release is available;
track [upstream issue #84](https://github.com/micromatch/braces/issues/84).
Migrating Tailwind alone would leave the ESLint dependency path.

**[GHSA-rj75-hqrm-r3gf](https://github.com/advisories/GHSA-rj75-hqrm-r3gf), moderate:**
quadratic selector parsing can exhaust CPU. Installed paths:

- `tailwindcss@3.4.19 → postcss-selector-parser@6.1.4`
- `tailwindcss@3.4.19 → postcss-nested@6.2.0 → postcss-selector-parser@6.1.4`

Patched parser 7.1.6 is outside both consumers' version-6 ranges. Await compatible
upstream updates or separately review a Tailwind migration; do not force a
major parser override or suppress these advisories.

Dependabot [PR #71](https://github.com/rick-mingyu-liu/TermPocket/pull/71)
was not adopted: its proposed removal of the vulnerable parser upgrades
Tailwind 3 to 4.3.3 without migrating the PostCSS configuration or styles.
CI fails because Tailwind 4 no longer provides the configured PostCSS plugin.
That migration needs separate review; the advisories remain open, with no
ignore rule or audit suppression added. The 2026-10-15 audit after the
compatible frontend updates still reports 7 high and 2 moderate findings.

The grouped frontend update's Radix Select 2.4.0 has an upstream callback-type
regression that rejects the transaction type selector's existing handler.
Select 2.4.1 fixes it without application changes. Dialog 1.3.1 and Dropdown
Menu 2.2.1 keep their focus-scope and dismissable-layer versions aligned with
Select, so nested controls share the same focus and layer state.

These dependencies process repository-controlled source patterns and CSS during
builds/linting in this application. They are not imported by application pages
and were absent from generated `.next/server/**/*.nft.json` page traces. This
bounds the observed application exposure; it does not remove the advisories.

## Verification

Next 16.4.3 (2026-11-04, Node 26.12 locally; CI runs 22): `npm ci`, lint (the
same single `transactions/edit/[id]` hook warning as `next lint` on main) and
`next build --webpack` passed, prerendering all 28 English and Chinese pages with
the full `common` store (470 en / 469 zh keys, matching the locale files). The
OCR shim chunk, not onnxruntime-web's own build, was bundled, and the two
legacy redirects are in the routes manifest. The first build failed prerendering
`/import`: its local `const process` captured the `process.env` reference that
Next 16's server-side hook optimisation inserts; renaming it fixed that.

Node 22.15.0: frontend production build, lint and locale checks passed. HTTP
smoke checks covered all eleven application pages, Chinese login, built JS/CSS
and four English/Chinese legacy redirects. The two existing transaction-page
hook warnings remain. Both manifests/lockfiles passed `npm ci --dry-run` with
scripts disabled and offline; CI must still perform fresh Linux installs.

The backend passed lint/build and all 783 tests with no skips on local PostgreSQL
17.11, using a dedicated throwaway database. Nodemailer 10's bundled declarations
replace `@types/nodemailer`; its Node 20+ requirement fits the project's Node 22
runtime. Offline CommonJS import, Gmail transport configuration and text/HTML
MIME generation passed; no email was sent and live SMTP was not tested.
